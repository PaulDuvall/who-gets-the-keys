# SPEC-001: Delivery pipeline

Intent: every change, the agent's or a human's, reaches the sandbox only through one pipeline, and each kind of bad change is stopped there with one named failure line.

Status: approved by signed commit.

| Term | Meaning |
|---|---|
| check | an npm script `check:<name>` |
| failure line | exactly one line `CHECK <name> FAILED: <identifier>` on standard output |
| scenario | a patch under `scenarios/` applied to `main` in a temporary worktree |
| approver | a key listed in `approvers.txt` in SSH allowed-signers format. From the rotation recorded in `docs/decisions/0003-approver-key.md`, every approver key is a FIDO2 security key (`sk-ssh-ed25519@openssh.com` or `sk-ecdsa-sha2-nistp256@openssh.com`) whose private half stays on the device. No check can prove where a private key lives; the approver keeps it there |
| gate | a human approval: an approver's signature on a commit, or a required reviewer's approval of a deployment to the `sandbox` or `probe` environment |

## Checks before `main`

`main` only moves to a commit on which the checks passed. Authors, agent or human, push a commit to a `candidate/` branch first, then push that same commit to `main`.

Pull requests are for review only. Every change lands by that fast-forward push, because GitHub's squash and rebase merges write new commits that the checks never ran on.

The pipeline runs once per push, on its tip. Commits below the tip are covered only by the checks that read history at the tip: trace, ratchet and signatures.

The ruleset names the GitHub Actions app, not the workflow. So a job named `checks` in any workflow, or a token with `checks: write` or `statuses: write`, can report the check. SPEC-001-R41 forbids both, but the commit being checked defines its own workflows. That gap is accepted until the signer moves out of the agent's reach (decision 0002, Phase 3).

The scenarios are not part of the checks before `main`. They run after landing, in `scenarios.yml` on `main`.

| ID | Requirement |
|---|---|
| SPEC-001-R40 | WHEN a commit is pushed to a branch matching `candidate/**`, THE pipeline SHALL run the checks, build, attest and receipt jobs on that commit. THE deploy job SHALL run only for `refs/heads/main`, and only after the receipt job has passed. `pipeline.yml` SHALL be triggered only by a push to `main` or to a branch matching `candidate/**`. Its checks job SHALL have no job-level condition, and every other job SHALL need it, directly or through another job, because GitHub reports a job that a condition skips as a success, which satisfies a required check. |
| SPEC-001-R41 | THE `protect main` ruleset that `scripts/bootstrap/github.sh` applies SHALL have no bypass actors and SHALL require the status check `checks` from the GitHub Actions app. Then `main` only moves to a commit on which `checks` passed. `scripts/bootstrap/github.sh` SHALL also allow merge commits and turn off squash and rebase merges, so that with linear history required no pull request merges in GitHub. No workflow other than `pipeline.yml` SHALL define a job named `checks`, and no workflow SHALL grant `checks: write` or `statuses: write`. |

## Task files

Tracer 2, slice T3a (`docs/notes/tracer-2-t3a.md`). An approver signs a task file, `tasks/<ID>.task.md`: the requirements one delivery serves, the paths it may produce, and the instruction. `tasks/` is a protected path, so a task file lands only in an approver-signed commit (SPEC-001-R12). The runner producer reads it instead of a free-text prompt (SPEC-001-R83, R87, R208), and two checks hold a candidate's commits to it. SPEC-001-R64 to R68, R72, R73 and R107 are decision 0004's drafts, thinned for the tracer as slice T2 thinned R83 to R89: a task file holds only `requirements` and `produces`, without 0004's `budget`, `verify` and `needs`; the scope check judges only the commits that carry a `Task:` trailer, so 0004's rule that every commit neither approver-signed nor touching only `docs/` and `proposals/` needs a task, its `missing Task trailer` failure and R67's `empty range` failure stay drafts; and the range's base is `main` as last fetched, not a signed policy. 0004's R69 to R71 stay drafts. Both checks run in the checks job after `npm run checks` and outside SPEC-001-R1's ordered fifteen, which are unchanged.

| ID | Requirement |
|---|---|
| SPEC-001-R64 | WHEN the task check runs for a task ID, THE task check SHALL require the ID to match `^TASK-[A-Z0-9-]{1,32}$`. IF it does not, THEN it SHALL print `CHECK task FAILED: invalid task id`. THE task check SHALL read the file only with `git show <base>:tasks/<ID>.task.md`. IF that fails, THEN it SHALL print `CHECK task FAILED: <ID> not found`. The file SHALL start with a line `---`. The lines up to the next `---` line are the front matter, and the rest is the body, the instruction. Each front matter line SHALL be `<key>: <value>`: the key, a colon, exactly one space and the value. The keys SHALL be `requirements` and `produces`, once each, each value a YAML flow list on one line, `[<entry>, <entry>]`, of 1 to 16 distinct entries with no quotes, white space or YAML indicator inside one. `requirements` SHALL hold requirement IDs. `produces` SHALL hold repository paths of letters, digits, `.`, `_`, `-` and `/`, with no empty, `.` or `..` segment and no leading `-`; an entry ending in `/` covers everything under it, as in `specs/protected-paths.txt`. Each `produces` entry SHALL lie within the runner producer's scope (SPEC-001-R208): under `src/`, `test/` or `docs/` with no segment that starts with `.`, or `traceability.md`. No `produces` entry SHALL cover, or lie under, `specs/`, `tasks/`, `approvers.txt` or a path in `specs/protected-paths.txt` at the base commit, compared without regard to letter case. IF a front matter line is not of that form or names another key, THEN it SHALL print `CHECK task FAILED: <ID> unknown key`. IF a key is missing or repeated, or its value breaks its rule, THEN it SHALL print `CHECK task FAILED: <ID> invalid <key>`, judging `requirements` first. A file with no front matter lacks both keys. The body SHALL be 1 to 8,000 bytes in UTF-8, because the producer passes it to Claude Code as one argument. IF the body holds only white space, THEN it SHALL print `CHECK task FAILED: <ID> empty body`. IF it is over 8,000 bytes, THEN it SHALL print `CHECK task FAILED: <ID> body over 8000 bytes`. |
